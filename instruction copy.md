Подкапотка, анализ текста
Да. Теперь уже можно собрать **целую подкапотную архитектуру анализа и подготовки текста LingLink**. Я бы сделал её максимально простой: без AI, без сложного NLP и без лишних проходов по тексту.

Главная идея:

> **Один раз разбираем текст → создаём индексы → во время этого же прохода находим слова, повторы, однокоренные слова и потенциальные грамматические конструкции → показываем результат пользователю → только после подтверждения сохраняем.**

# 3. Нормализация

Первое — приводим текст к технически нормальному виду.

```ts
function normalizeText(text: string): string {
  return text
    .normalize("NFC")
    .replace(/\r\n/g, "\n")
    .replace(/[ \t]+/g, " ")
    .trim();
}
```

Но здесь важно:

**мы не должны уничтожать форматирование, которое может быть важно пользователю.**

Поэтому лучше иметь:

```ts
originalText;
normalizedText;
```

```ts
interface NormalizedText {
  original: string;
  normalized: string;
}
```

# 5. Tokenization

Каждое предложение разбиваем не просто через `.split(" ")`.

Нам нужны **tokens**:

```ts
type TokenType = "word" | "punctuation" | "number" | "other";

interface Token {
  id: ID;

  sentenceId: ID;

  position: number;

  text: string;

  normalized: string;

  type: TokenType;
}
```

Например:

```text
Вчера я пошел в магазин.
```

↓

```ts
[
  {
    text: "Вчера",
    normalized: "вчера",
    type: "word",
  },
  {
    text: "я",
    normalized: "я",
    type: "word",
  },
  {
    text: "пошел",
    normalized: "пошел",
    type: "word",
  },
  {
    text: "в",
    normalized: "в",
    type: "word",
  },
  {
    text: "магазин",
    normalized: "магазин",
    type: "word",
  },
  {
    text: ".",
    normalized: ".",
    type: "punctuation",
  },
];
```

# 6. Создаём индексы

Вот это важная часть.

Мы **не хотим потом постоянно проходить весь массив текста**.

После токенизации строим индексы.

### Индекс слов

```ts
Map<string, Token[]>;
```

Например:

```text
"пошел" → [token_3, token_11]
"магазин" → [token_5]
"я" → [token_2, token_8]
```

Это сразу даёт частотность.

---

### Индекс нормализованных слов

```ts
Set<string>;
```

Например:

```ts
{
  ("вчера",
    "я",
    "пошел",
    "в",
    "магазин",
    "там",
    "купил",
    "хлеб",
    "и",
    "молоко",
    "потом",
    "домой");
}
```

Теперь:

```ts
wordIndex.has("магазин");
```

мгновенно отвечает:

> есть.

# 10. Поиск однокоренных

Берём:

```ts
word.rootWords;
```

Например:

```text
пошел
 ├── пойти
 ├── поход
 └── приходить
```

Но нас интересует только:

> какие из этих слов **есть в текущем тексте?**

У нас уже есть:

```ts
wordIndex: Map<string, Token[]>;
```

Поэтому ищем соответствующие `Word` и проверяем:

```ts
textWordIds.has(rootWordId);
```

Или можно заранее иметь:

```ts
Set<ID>;
```

найденных `Word`.

Получаем:

```ts
{
  rootWordId: "456",
  occurrences: 1
}
```

# 11. Не проверяем одни и те же rootWords много раз

Допустим:

```text
пошел
пошел
пойти
```

`пошел` встретился два раза.

Но:

```text
rootWords
```

проверять два раза бессмысленно.

Поэтому:

```ts
const checkedRootWords = new Set<ID>();
```

И:

```ts
if (checkedRootWords.has(rootWordId)) {
  continue;
}

checkedRootWords.add(rootWordId);
```

# 12. Грамматические конструкции

Теперь абсолютно аналогичный принцип.

Нашли:

```text
気
```

В базе:

```ts
grammarConstructions: ["construction_1", "construction_5", "construction_8"];
```

Получаем эти конструкции.

Например:

```text
construction_1 = 気をつける
construction_5 = 気になる
construction_8 = 気がする
```

Теперь проверяем:

> есть ли эта конструкция в текущем тексте?

---

# 13. Но конструкция может изменяться

Это важный момент, который мы уже заметили.

В базе:

```text
気をつける
```

а в тексте:

```text
気をつけて
```

Поэтому `GrammarConstruction` лучше иметь:

```ts
interface GrammarConstruction {
  id: ID;

  language: LanguageCode;

  construction: string;

  forms: string[];

  translations: Record<LanguageCode, ID[]>;

  type: GrammarConstructionType;

  relatedWords: ID[];

  createdBy: ID;

  createdAt: Timestamp;

  updatedAt: Timestamp;
}
```

Например:

```ts
{
  construction: "気をつける",

  forms: [
    "気をつける",
    "気をつけて",
    "気をつけた",
    "気をつけない"
  ]
}
```

---

# 14. Проверяем конструкции

Получили:

```ts
construction.forms;
```

и ищем их в нормализованном тексте.

Но тут тоже используем:

```ts
checkedConstructions = new Set<ID>();
```

Поэтому если:

```text
気
気
気
```

встречается 3 раза, одна и та же конструкция проверяется только один раз.

---

# 15. Лучше проверять конструкцию не через весь текст

Есть два варианта.

### Плохой:

```ts
for each word
  for each construction
    text.includes(construction)
```

Можно получить много повторных операций.

### Лучше:

У нас уже есть позиция токена.

Например:

```text
気 を つけ て 帰 って
```

Если конструкция начинается с `気`, мы проверяем только участок текста рядом с этим `気`.

То есть:

```text
найдено 気
     ↓
его grammarConstructions
     ↓
проверяем формы конструкции
     ↓
совпадает ли последовательность токенов
     ↓
создаём occurrence
```

Это особенно важно для длинных текстов.

### Если конструкция простая:

```text
気をつけて
```

ищем последовательность токенов.

### Если конструкция сложная:

```text
〜わけではない
```

позже можно будет добавить специальный matcher.

Но **MVP не надо делать универсальный японский морфологический анализатор**.

# 17. Дедупликация

После анализа у нас может быть:

```text
пошел
пошел
пошел
```

Но `uniqueWords` должен содержать:

```text
пошел ×3
```

Поэтому:

```ts
Map<ID, AnalyzedWord>;
```

где ключ:

```text
wordId
```

А если слова ещё нет в базе:

```text
normalizedWord
```

# 22. Translation Phase

Система группирует слова:

```text

магазин ×1
купил ×1
хлеб ×1
молоко ×1
```

А не показывает:

```text
пошел
пошел
магазин
купил
...
```

Пользователь переводит уникальные слова.

Если есть перевод:

```text
магазин

✓ 店
  店舗
  商店

[Добавить вариант]
```

Если нет:

```text
молоко

[Введите перевод]
```

# 26. Очень важное разделение

В итоге у LingLink будут три совершенно разные стадии:

### ① ANALYSIS

```text
Что вообще находится в тексте?
```

Система сама:

- делит предложения;
- делит на слова;
- считает повторения;
- ищет слова в базе;
- ищет однокоренные слова;
- ищет известные грамматические конструкции;
- собирает статистику.

---

### ② TRANSLATION

```text
Как это перевести?
```

Здесь участвует community:

- пользователь предлагает перевод;
- выбирает существующий;
- добавляет новый;
- другие пользователи голосуют;
- можно исправлять.

---

### ③ LEARNING

```text
Как этот текст используется для обучения?
```

И здесь уже работает твоя первоначальная механика:

```text
Текст
 ↓
5 новых слов
 ↓
текст с этими словами
 ↓
следующие 5
 ↓
текст
 ↓
...
```

А пользовательские `WordProgress` определяют:

```text
это слово уже знаю
```

поэтому известные слова сразу отображаются на изучаемом языке.

---

## И архитектурно самое важное

Я бы **не делал один огромный `analyzeText()`**.

Разделил бы сервисы:

```text
text/
│
├── normalizeText.ts
├── sentenceSplitter.ts
├── tokenizer.ts
├── wordAnalyzer.ts
├── rootWordAnalyzer.ts
├── constructionAnalyzer.ts
├── textStatistics.ts
└── textAnalysisService.ts
```

А наверху:

```ts
analyzeText();
```

просто координирует их.

Получается очень чистая схема:

```text

                    │
TEXT → tokenize → word analysis
                    │
                    ├── rootWords
                    │
                    └── grammarConstructions
                              │
                              ▼
                       Analysis Result
                              │
                              ▼
                           Preview
                              │
                              ▼
                           Translate
                              │
                              ▼

                              │
                              ▼
                           Learning
```

# 24. Что я бы сделал главным экраном

В итоге пользовательский цикл очень простой:

```text
                 LINGLINK
                     │
          ┌──────────┴──────────┐
          ↓                     ↓
       TEXTS                  WORDS
          │                     │
          ↓                     ↓
       TEXT                 WORD
          │                     │
          ↓                     ↓
    Choose 5 words        Find texts
          │                     │
          ↓                     │
       READ ←───────────────────┘
          │
          ↓
    Learn in context
          │
          ↓
    Next 5 words
          │
          ↓
       Next text
```

И вот это, на мой взгляд, **должно быть всей философией UI**.

Не 20 кнопок, не уровни, XP, streaks, монетки, энергия и прочий Duolingo-цирк. Пользователь пришёл **читать интересные тексты и постепенно превращать незнакомый язык в знакомый**.

А community находится рядом и незаметно поддерживает эту систему: люди добавляют тексты, переводят слова, создают конструкции, исправляют ошибки и тем самым улучшают материалы для следующих пользователей.
